## Configuration {#configuration}

`implemented`

Components: `ArmDTPlatform`.

### Hardware and dependencies

- SoC: SDM710/712 \(Kryo 360, 2x Cortex-A75 + 6x Cortex-A55\), GIC-500 GICv3, 19.2 MHz Qualcomm XO counter, PSCI over SMC.
- DRAM: 4 GiB model, one contiguous window at 0x1\_0000\_0000 + 0x7e2c\_0000 above the ABL reservations.
- Target OS: the unchanged iPad7,1 iPadOS 17.7.11 \(21H461\) restore image, the same kernelcache the UniXNU iPadOS profile ships.
- Shared SoC layer: UniXNU-sdm710-common, pinned in feeds.toml because SDM712 is the same die with a 100 MHz higher big-core clock.

### Configuration

- board.toml is format 2 \(schema\_version = 2\), selects soc\_source = sdm710 and os\_profile = ipados-17.7.11-21H461, and includes ArmDTPlatform, ArmCpu, XnuPrelink and DarwinBoot.
- dts/rmx1971.dts declares memory@100000000 \(0x1\_0000\_0000 + 0x7e2c\_0000\) and the eight cores with their affinities, and includes sdm710.dtsi for the GIC, PSCI and counter.
- configs/rmx1971\_defconfig starts from the shared sdm710 first-console configuration unchanged: the SoC half is identical, and diverging before the first hardware run would make a porting error indistinguishable from a tuning change.
- kernel.patch\_series appends device:patches/xnu/series after the arch, SoC and OS series, so the board's own XNU change applies last.

### Procedure

- ./unixnu fetch sdm710; ./unixnu defconfig rmx1971\_defconfig -D .; ./unixnu status --json
- python3 scripts/porting-record.py check --device . \(from a UniXNU checkout\) validates this record against board.toml.

### Development findings

- Every number here comes from the handset: the partition geometry, the DRAM window and the timer rate were read off the device \(part list, scsi read, and the kernel's own panel\) before being written down.
- SDM712 differs from SDM710 only in the top CPU OPP \(2.3 against 2.2 GHz\) and the GPU clock; nothing in the boot path needs a 712-specific description, so the shared SoC layer is used unchanged rather than copied.
- The device tree is the one place where U-Boot and XNU disagree and both are right: U-Boot's board tree must describe the LOW half \(0x8000\_0000 + 0x7e2c\_0000\) because that is the memory it owns and relocates in, while XNU's tree describes the HIGH half, which is the only contiguous window left.

### Completion criteria

- The record validates against board.toml, the device tree compiles, and the configuration resolves through all four profiles \(arm64, sdm710, iPadOS 17.7.11, this board\).

### Current limits

- Only the first-console configuration is exercised; nothing that needs a storage driver, GPU or input device is configured yet.

### Next action

- Add the storage area's device evidence once the UFS driver completes a read on hardware, and extend the record with each peripheral as it is brought up.

## Firmware and boot {#firmware}

`device-verified`

Components: `DarwinBoot`.

### Hardware and dependencies

- Firmware: OPPO/realme ABL \(no boot command over fastboot\), U-Boot 2026.07 built by this repository, UEFI from its EFI loader.
- Payload volume: 128 MiB FAT32 on LUN0 partition 8 \(vm-system, LBA 0x2d00\), because that partition is unused by this project and writable by the ABL.
- UniXNU.efi and DarwinBoot.efi built from source in CI; the kernel arrives from the macOS kernel workflow.

### Configuration

- U-Boot bootcmd: \`bootefi bootmgr\`, then a fallback that reads a bare PE image from logfs \(LUN4 LBA 0x19391\) and starts it with \`bootefi 0xa0000000:400000\`.
- unixnu.toml entries: default = "xnu", timeout = 3, \[\[driver\]\] Payloads/DarwinBoot.efi, \[\[entry\]\] xnu -&gt; Payloads/kernel.macho.
- Kernel arguments include boot-progress=2 sheng-smp=1 cpus=8 armcpu-timer-intid=19 sheng-pmgr=2 amfi\_get\_out\_of\_my\_way=1 rd=ufsroot0 ufsroot=userdata.

### Procedure

- fastboot flash vm-system rmx1971-payload.img; fastboot flash boot uboot-rmx1971-boot.img; fastboot reboot
- fastboot boot is not usable on this ABL: it transfers the image and then fails with FAILED \(remote: 'unknown command'\).

### Development findings

- The ABL matches the appended DTB table by qcom,msm-id and ignores androidboot.dtb\_idx, so the image cannot choose its entry; every entry in the vendor table is patched with the framebuffer and memory nodes instead.
- U-Boot's EFI boot manager enumerates block devices, sees the UFS partitions as SCSI block devices with partition children, and starts \\EFI\\BOOT\\BOOTAA64.EFI from the FAT volume; no vendor-specific plumbing was needed.
- bootefi accepts an explicit :size for images that were read into memory directly; without it the loader answers 'No UEFI binary known at ...' because it only trusts addresses it recorded itself.

### Completion criteria

- ABL starts U-Boot, U-Boot starts UniXNU.efi from the payload volume, UniXNU starts DarwinBoot, DarwinBoot enters the kernel, and the kernel reaches its own console.

### Current limits

- USB gadget fastboot is not usable: \`fastboot usb 0\` waits for a host that never enumerates, most likely because VBUS is absent at the moment the gadget is initialised. Development therefore goes through the ABL on every iteration.
- The payload volume lives on vm-system, so a factory reset that reformats that partition removes it; the fix is one \`fastboot flash vm-system\`.

### Next action

- Retry the USB gadget with the cable attached before power-on, to see whether enumeration depends on VBUS at init time.

- Boot CPU numbering comes from the ADT; the Apple ARM CPU platform expert looks up /cpus by matching name.

### Configuration

- dts/rmx1971.dts lists cpu@0..cpu@700 with their reg, enable-method = "psci" and the A55/A75 compatible strings.
- Kernel arguments: sheng-smp=1 cpus=8 armcpu-self-ipi=1 armcpu-timer-intid=19.

### Procedure

- Build the payload, boot it, and read TOPO/CLK/SMP off the boot-progress panel.

### Development findings

- Without the IONameMatch rewrite Apple's CPU class claims cpu0..cpu7 by prefix and the kernel panics with 'CPU configuration in device tree is invalid'; the rewrite is a same-length string substitution, so the kernel image is not relaid out.
- All eight cores reach step7 with the non-Apple timer INTID; the counter rate reported by the kernel \(19200000\) equals the device tree's timebase-frequency, and the derived milliseconds match the wall clock of the boot.

### Completion criteria

- Every secondary CPU reports its entry checkpoint and takes timer interrupts, and the delay calibration agrees with the device tree.

### Current limits

- CPU frequency scaling is not implemented: the kernel runs at whatever the bootloader left. The 2.3 GHz SDM712 OPP does not exist in the shared sdm710 clock table.

### Next action

- Add the 2.3 GHz big-core OPP to a board clock table once the root device works; it is a table entry, not a boot-path change.

## Memory and DMA {#memory}

`device-verified`

### Hardware and dependencies

- DRAM: 4 GiB total; below 4 GiB the ABL and its reserved-memory carve-outs fragment everything, and the only contiguous window is 0x1\_0000\_0000 + 0x7e2c\_0000.
- DarwinBoot allocates the kernel's owned window from the EFI memory map it was given, not from the device tree.

### Configuration

- board.toml: dram\_size = 0x7e2c0000, \[payload.adt\] owned\_memory\_size = 0x20000000 \(512 MiB\).
- dts/rmx1971.dts: memory@100000000 &\#123; reg = &lt;0x1 0x0 0x0 0x7e2c0000&gt; &\#125;.

### Procedure

- Boot and read MEM totalMiB / free4K / wired from the panel; the three must add up.

### Development findings

- Unset owned\_memory\_size gives the 256 MiB default, which is what the first boot reported \(free4k 173 MiB + wired 83 MB\).
- Asking for the whole 0x7e000000 fails before the kernel starts with 'rmx1971 first boot returned: out of resources': the EFI map is U-Boot's low half, where the ABL reservations end at 0xB8300000, the frame buffer holds 10 MiB at 0x9c000000 and U-Boot relocates to the top, leaving a little over 1 GiB contiguous that also has to hold the 52 MiB kernel image.
- 512 MiB boots with wired=22411 and free4K=108298, and is the value the port ships.

### Completion criteria

- The kernel owns a contiguous window large enough for the kernel image plus userland, and every reserved region is accounted for.

### Current limits

- The full 1.97 GiB requires U-Boot's memory node to describe the high half as well; until then the kernel is limited to 512 MiB of the window the device tree declares.

### Next action

- Extend U-Boot's /memory node to cover 0x1\_0000\_0000 + 0x7e2c\_0000 and re-measure the largest contiguous EFI allocation before raising owned\_memory\_size.

### Evidence

- `device`: [MEM totalMiB=512 free4K=108298 wired=22411 after owned\_memory\_size = 0x20000000; the 0x7e000000 attempt reported 'out of resources' instead.](https://github.com/AppleCampus/UniXNU-rmx1971/blob/e0c2df8bedf4292066372aa325c2ead0db02d1c5/docs/bring-up.md)

## Storage and root {#storage}

`implemented`

### Hardware and dependencies

- Storage: UFS \(ufshc@1d84000, UFSHCI 2.1\) with six LUNs and 4096-byte blocks; no eMMC, so the shared layer's SDCC1 eMMC kit does not apply.
- The host is left enabled with the link up by U-Boot, exactly as the ABL leaves it, so the XNU driver does not initialise the PHY or the link.

### Configuration

- patches/xnu/sweet-ufs-root.patch adds bsd/dev/sweet\_ufs.c, bsd/conf/files, an IOKitBSDInit probe and a vfs\_mountroot probe that assigns rootdev.
- Kernel arguments: rd=ufsroot0 ufsroot=userdata \(default partition name is userdata, GPT entry 14 at LUN0 LBA 0x198900\).
- U-Boot side: patches/uboot/0001-clk-sdm670-add-ufs-phy-rx-symbol-1.patch adds GCC\_UFS\_PHY\_RX\_SYMBOL\_1\_CLK at 0x770a8, without which ufshcd fails to enable the controller with -ENOENT.

### Procedure

- fastboot flash vm-system rmx1971-payload.img, boot, and read the driver's verdict on the panel's stage line.
- From U-Boot: part list scsi &lt;lun&gt; and scsi read to verify the GPT and read a partition by LBA.

### Development findings

- Six LUNs totalling 63.99 GB: LUN0 58.6 GiB Android, LUN1 xbl/xbl\_config, LUN2 an empty GPT, LUN3 ALIGN\_TO\_128K\_1/cdt/ddr, LUN4 and LUN5 the firmware half including boot at LBA 0xc505.
- LUN0's GPT has 32 slots and 14 entries, while the ABL knows 64 partitions whose reversed order starts with those same 14: the table on LUN0 is a truncated copy, and the firmware partitions are on LUN4/LUN5 with tables of their own.
- scsi read of LUN4 LBA 0xc505 returns 'ANDROID\!', so the running boot image is readable from U-Boot by fixed LBA.
- The first XNU driver attempt added a branch inside IOFindBSDRoot and produced no output at all: the panel showed vfs\_mountroot entered every five seconds, which means rootdev stayed NODEV and bdevvp\(\) failed before any filesystem was asked. The probe therefore belongs at the top of vfs\_mountroot\(\), and it must assign rootdev rather than only report.
- The driver keeps its verdict on the boot-progress stage line because everything it printf\(\)s scrolls off a console that retains only the latest seven lines; the hook is a weak reference so the bootstrap pass, which links without the kit archives, still links.

### Completion criteria

- The driver reports the partition geometry on the stage line, the kernel mounts a filesystem from it, and userdata is reachable without touching any other partition.

### Current limits

- Read-only and not yet observed on hardware. userdata currently holds Android's encrypted filesystem, so the first successful probe is still expected to fail the mount with errno 19.
- Writes, 4 GiB-plus DMA and the speed work from the same source project are not ported.

### Next action

- Boot the payload carrying the vfs\_mountroot probe and read its stage line: 'UFS ok: ...' moves the problem to the filesystem, 'UFS: init failed N' names the stage \(5 host handover, 6 no GPT, 2 no such partition, 12 DMA\).

### Evidence

- `source`: [Read-only UFS block driver, conf/files entry, IOKitBSDInit probe and the vfs\_mountroot probe that assigns rootdev.](https://github.com/AppleCampus/UniXNU-rmx1971/blob/e0c2df8bedf4292066372aa325c2ead0db02d1c5/patches/xnu/sweet-ufs-root.patch)
- `host`: [Kernel builds with the driver; the assembled payload's kernel.macho carries the driver strings and both probes.](https://github.com/AppleCampus/UniXNU-rmx1971/actions/runs/41022700761)
  Command: <code>./unixnu build kernel --defconfig rmx1971_defconfig --device AppleCampus/UniXNU-rmx1971</code>. Revision: `14a9ae187e345111e85a24674cbad57d0020ccfd`.

### Completion criteria

### Current limits

- Brightness control, panel backlight and any GPU-accelerated presentation are absent; everything is CPU copies into the splash buffer.

### Next action

## Diagnostics {#diagnostics}

`device-verified`

### Hardware and dependencies

### Configuration

- Kernel: boot-progress=2 selects the full panel; the console pane keeps the latest seven lines.

### Procedure

- Read the stage line and the eight PC samples, then resolve a PC against the kernel's LC\_SYMTAB.

### Development findings

### Completion criteria

### Current limits

- The console pane holds seven lines; anything that prints more scrolls away, which is why drivers must pin their conclusions on the stage line.

### Next action
