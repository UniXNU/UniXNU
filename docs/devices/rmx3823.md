## Configuration {#configuration}

`implemented`

Components: `ArmDTPlatform`, `ArmCpu`, `SoftwareAES`, `XnuPrelink`, `DarwinBoot`.

### Hardware and dependencies

- SM8550 kalama SoC support from UniXNU-sm8550-common, pinned at a9f45dc6.

### Configuration

- board.toml sets soc\_source = sm8550, defconfig = rmx3823\_defconfig, device\_tree.source = device:dts/board.dts.
- dts/board.dts includes sm8550.dtsi and enables ufs, ufsphy, gpu, gmu and gpu\_smmu.
- configs/rmx3823\_defconfig carries only board deltas; the arch, soc and os fragments supply the base.

### Procedure

- Read the device over adb: getprop, /proc/cpuinfo, /sys/devices/soc0, /sys/firmware/devicetree/base/reserved-memory.
- Unpacked the stock dtbo.img \(big-endian dt\_table\_header, 4 entries\) and decompiled each DTB.
- Ran \`unixnu defconfig rmx3823\_defconfig --device .\` and inspected the merged out/rmx3823/&lt;profile&gt;/rmx3823/.config.

### Development findings

- soc\_id 519 and machine KALAMA match sm8550.dtsi: 3x A510, 2x A710, 2x A715, 1x X3, and GPU Adreno740v2.
- Page size is 4096, which the Sm8550Platform kit requires; a 16K-page SM8550 would not work.
- dtbo entries 1 and 2 carry qcom,msm-id 0x207 \(519\) and are the board overlays; entries 0 and 3 carry 0x258/0x259 and do not match this device.
- soc:configs/sm8550.config sets CONFIG\_XNU\_NATIVE\_ADRENO=y while the device defconfig is applied last, so the two must be changed together with \[components\].
- unixnu builds only on macOS and Linux. On Windows, defconfig and status run, but the kernel, payload and firmware steps do not.
- .github/workflows/build.yml builds from this repository alone: it checks out upstream UniXNU/UniXNU as the engine, so the board needs no fork of the engine repository.
- The firmware checkout is Janit8r/uefi-rmx3823, a fork of UniXNU/uefi-sheng on branch sheng. \[firmware\] now names config, dsc, fd, submodules and the full PACKAGES\_PATH; Mu\_Basecore is left out because the engine supplies it as &\#123;edk2&\#125;.
- rmx3823Pkg is derived from Platforms/Qualcomm/qrd8550Pkg rather than nuwaPkg or shengPkg: RMX3823 is a non-Xiaomi board on the same Qualcomm boot\_images baseline, and no rmx3823 set exists in Device-Binaries or Silicium-ACPI, so Binaries/qrd8550 and the qrd8550 ACPI tables are reused deliberately.
- rmx3823Pkg is not buildable with Mu-Silicium's build\_uefi.py: it carries UniXNUPkg and DarwinBootPkg in its DSC/FDF the way shengPkg does, and build\_uefi.py has no PACKAGES\_PATH for them. It must go through ./unixnu build firmware --uefi.
- rmx3823Pkg compiles. uefi-rmx3823 run 41276749199 built it on ubuntu-24.04 with UniXNU.efi, UniXNUDxe.efi, UniXNURamDiskDxe.efi, UniXNULib and DarwinBoot.efi in the volume, and the firmware volume came out at exactly 0x300000 bytes.
- That build needed a fix first: \[boot\_image\] carried only header\_version, so build\_uefi.py fell back to mkbootimg.py's defaults and produced kernel\_addr 0x10008000 with pagesize 2048. SM8550's DDR starts at 0x80000000, so that address is not memory. The engine's own bootimg step uses different defaults \(base 0, pagesize 4096\), which is why the two paths disagreed silently. All five fields are now explicit.
- The stock uefi.elf is an ELF with a single 3 MiB LOAD segment at 0xA7000000, which is where the vendor firmware volume actually lives; the entry point is 0xA7000000.
- uefi.elf carries its uefiplatLA.cfg as an embedded string blob \(the stock UEFI parses that text at boot: PlatConfigFileName = "uefiplatLA.cfg"\). Extracting it gives the authoritative memory map: Version 3, MaxMemoryRegions 74, 39 regions in use - 25 DDR, 2 IMEM, 12 register windows.
- \[uefi\_fd\] moved from 0xA7100000+0x300000 to 0xA7000000+0x400000, the carveout the vendor cfg reserves as "UEFI FD". The stock image is 3 MiB of that 4 MiB window, so this occupies exactly the reserved range and leaves 1 MiB of headroom.
- The ADT generator reads exactly one contiguous device\_type = memory range from the hardware DTS and rejects anything else; /chosen/memory-map only ever carries RAMDisk, TrustCache, GpuAddon and RootPolicies. reserved-memory in dts/board.dts therefore does not become an ADT reservation - the handoff range is the only thing that keeps XNU out of firmware memory.

### Completion criteria

- All source pins resolve; every selected component has a record; status shows the intended overrides and patch order.

### Current limits

- Installed RAM is still inferred from MemTotal 23645600 kB. The vendor memory map stops at 0x100000000 and does not state the DRAM size.
- Panel and touch are not identified; the stock boot.img is header\_version 4, so the base device tree lives in vendor\_boot.img, which is not available.
- Nothing has run on hardware. Whether the RMX3823 ABL accepts the boot image is unverified; a rejection shows as the device dropping to fastboot with nothing on screen.

### Next action

- Flash the CI boot image and capture the serial log; then widen the handoff range once the booter's carveout exclusions are verified.

## Memory and DMA {#memory}

`implemented`

### Hardware and dependencies

- The stock firmware set: uefi.elf \(the vendor UEFI, 3 MiB at 0xA7000000\), tz.mbn, uefi\_sec.mbn, boot.img and recovery.img.
- The board's uefiplatLA.cfg, recovered from the string blob inside uefi.elf.
- The 28 reserved-memory regions previously listed from /sys/firmware/devicetree/base/reserved-memory, addresses only.

### Configuration

- dts/board.dts declares one contiguous handoff range, memory@bab00000, reg = &lt;0 0xbab00000 0 0x0d1c0000&gt;.
- 0xBAB00000 + 0x0D1C0000 is the "DXE Heap" entry of the vendor memory map and the only region it marks EFI\_RESOURCE\_SYSTEM\_MEMORY with EfiConventionalMemory.
- aop\_cmd\_db\_region@81c60000 keeps 0x20000, which the map supports: "AOP" is 0x81C00000 + 0xA0000 and aop\_config\_merged@81c80000 starts immediately after it.
- smem\_region@81d00000 corrected from 0x400000 to 0x200000, the map's "SMEM" size. The old value would have covered adsp\_mhi@81f00000, which begins where SMEM ends.

### Procedure

- Parsed the ELF program headers of uefi.elf: one LOAD segment, vaddr 0xA7000000, filesz 0x300000, entry 0xA7000000.
- Located the embedded config text by searching for "\[MemoryMap\]" and dumped it between the \[Config\] and \[ConfigParameters\] markers, replacing NULs with newlines.
- Parsed both the cfg and MemoryMapLib.c and compared address, size and name row by row; 39 rows, exact match, no overlaps within any section.
- Cross-checked against tz.mbn's program headers and the dtbo overlay's carveout addresses.

### Development findings

- The vendor memory map has 39 regions: 25 DDR, 2 IMEM and 12 register windows. That is the whole of what UEFI may touch, and it is now what rmx3823Pkg carries.
- tz.mbn's entry point and first LOAD vaddr are 0x14680000, exactly the map's "IMEM Base", and its 0xd830a000 segment falls inside "TZApps Reserved" 0xD8800000 + 0x07400000. Two independent files agreeing on the same extraction.
- The map stops at 0x100000000 and does not describe installed RAM, so 24 GiB remains an inference from MemTotal. The DDR base 0x80000000 is confirmed by the map's first entry.
- Twelve of the device's 28 reserved regions fall in gaps the vendor map does not describe at all - chipinfo@81cf4000, adsp\_mhi@81f00000, global\_sync@82600000, tz\_stat@82700000, mpss@89800000, mpss\_dsm@d4d00000, xbl\_sc@d8100000, cpucp\_fw@d8140000, qtee@d8300000, oem\_vm@f7c00000, oem\_vm\_swiotlb@f7b00000, trust\_ui\_vm@f3800000 - so UEFI neither reserves nor maps them.
- The handoff range cannot be the whole 24 GiB: the carveouts are interleaved through the low address space and no single contiguous range avoids them. The vendor's "Kernel" window 0xA8000000 + 0x10000000 is specifically wrong, because it is where ABL loads the boot image and this device's boot partition is 192 MiB, matching payload.size\_mib.
- reserved-memory in dts/board.dts does not protect anything: the ADT generator only reads the memory node, and /chosen/memory-map carries RAMDisk, TrustCache, GpuAddon and RootPolicies only. The nodes are kept as verified documentation and because ShengGmuCommandDbInputs and the GPU driver name those addresses.

### Completion criteria

- All handoff regions are accounted for and each enabled DMA engine accesses its allocated range with the documented cache policy.

### Current limits

- The handoff range is 210 MiB, enough to bring up but not to run a full system. Widening it needs the booter to exclude the carveouts, which is unverified.
- Individual extents inside "PIL Reserved" are still unknown; only the enclosing range 0x8A800000 + 0x18280000 is established.
- mpss@89800000 sits below 0x8A800000 and is not covered by any map entry, so its extent is unknown.
- Installed RAM is unconfirmed; the map does not state it.

### Next action

- Verify the handoff range on hardware, then extend it once the booter's carveout exclusions are established.

### Evidence

- `source`: [Handoff range 0xBAB00000 + 0x0D1C0000, corrected SMEM size, and the 28 device regions reconciled against the firmware map into covered, collectively-covered and undescribed groups.](https://github.com/Janit8r/UniXNU-rmx3823-new/blob/e75657692fc4eca7d49dba26941690264dd1dc09/dts/board.dts)

### Development findings

- The panel itself is still unidentified. The overlay carries the DSI controller \(v2.7\), PHY \(v5.2\) and display nodes, but the panel node lives in the base device tree, which is in vendor\_boot.img - and boot.img is header\_version 4, so it does not carry it either.
- Two facts about the panel are established. Its resolution is 1240x2772, confirmed independently by the touch node's display-coords 0x4D8 x 0xAD4, and the touch node reports panel\_type 7.
- Display Reserved is 0xB8000000 + 0x02B00000 and Display Demura is 0xA2A80000 + 0x02B00000 in the vendor memory map, so the framebuffer carveouts are known even though the panel is not.

### Completion criteria

- A known frame appears with correct geometry and colors, then userland presentation and backlight controls work.

### Current limits

- No panel model, and therefore no initialisation sequence. vendor\_boot.img or a device-side /sys/firmware/fdt dump is required.
- The firmware volume runs with RMX3823\_VENDOR\_HW = 0 and publishes a GOP over the framebuffer ABL already scans out, so this does not block bringing up the menu.

### Next action

- Obtain vendor\_boot.img or a device FDT dump to identify the panel, then extract its init sequence.

## Input {#input}

`planned`

### Hardware and dependencies

- Identify the input hardware, resources and existing component interfaces for this board.
- The touch fragments in dtbo.img entry 1, machine Kalama MTP,zonda-A/B.

### Configuration

- Record the board.toml fields, DTS properties and defconfig values used for input.

### Procedure

- Follow the input stage in the porting guide and record the actual commands.
- Decompiled the stock dtbo.img and read fragment@66, which carries all three touch candidates.

### Development findings

- The active touch controller is a Synaptics S3910 over SPI, from fragment@66 of the dtbo overlay. synaptics\_tcm@0 is the only one of three candidates marked status = ok; goodix-berlin@5d and synaptics\_tcm\_hbp@0 are both disabled.
- Wiring from that node: SPI CS0 at 15 MHz, IRQ GPIO 25 with interrupts = &lt;25 0x2008&gt; \(falling edge, ONESHOT\), reset GPIO 24, avdd GPIO 10, TX 17 x RX 38, panel\_type 7, firmware AB641.
- drivers/ShengNovatekTouch does not apply to this board; a Synaptics TCM \(SPI\) implementation is needed instead.
- The same overlay carries a goodix node for a 1080x2400 panel, so the model ships with more than one touch and panel SKU. This unit is the 1240x2772 + S3910 combination.

### Completion criteria

- Touches map to the display, simultaneous contacts keep stable IDs, release events arrive, and buttons produce expected HID reports.

### Current limits

- No Synaptics TCM driver exists in this tree yet.
- The SPI bus instance is not identified: the overlay fragment targets a phandle rather than a named controller, so the bus number and its GPIO controller base still have to be resolved.
- Touch firmware AB641 has not been extracted.

### Next action

- Resolve the SPI bus instance and GPIO controller, then write a Synaptics TCM reader against the addresses above.

### Evidence

- `source`: [Section 10.4 records the S3910 node, its status, bus, GPIOs and panel\_type, and why the two other candidates are disabled.](https://github.com/Janit8r/UniXNU-rmx3823-new/blob/e75657692fc4eca7d49dba26941690264dd1dc09/docs/hardware-survey.md)
